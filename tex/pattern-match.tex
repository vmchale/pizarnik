\section{Introduction}

Pizarnik's approach to pattern-matching is based on commitment to the idea of pattern-matching as inverse\cite{ehrenberg2009} and suggestive notation from linear logic ($\&$, ``with'', is dual to disjunction, $\oplus$) \cite{munchmaccagnoni}.

The actual machinery for extensible cases has already been accomplished by Blume, Acar, and Chae \cite{blume2006} with the end of solving the expression problem.

\section{Extensible Pattern Matches}

Suppose we define an algebraic data type

\begin{verbatim}
type Bool = `true ⊕ `false;
\end{verbatim}

The literal \verb|`true| pushes a tag\footnote{Inspired by symbols (e.g. \verb|`blue|) in k, which are preceded by symbols (\verb|'red|) in Lisp.}  \verb|`true| onto the stack. We assign it the type \verb|-- `true|. Its inverse \verb|`true⁻¹| pops a value of type \verb|`true| off the stack and hence the atom \verb|`true⁻¹| has type \verb|`true --| (inverse exchanges left and right).

% negation as fruitful interaction (orthogonality) rather than situation with principle of explosion we have in classical logic
% also left-right, exactly at beta-reduction... which is no doubt a fruitful interaction!

In linear logic, one has $(G\oplus H)^\bot = G^\bot \& H ^\bot$. To pop off a value of type \verb|Bool = { `true ⊕ `false }|, one writes \verb|{ `true⁻¹ & `false⁻¹ }| in Pizarnik. Or-patterns in other programming languages work like linear logic's \verb|&|, which identifies a product of deconstructors with a deconstructor for a sum---the De Morgan laws.\footnote{The duality is worth noting: if we have two choices for returning a value of type $A\oplus B$ then a function accepting $A\oplus B$ must \textit{provide} two pattern match arms.}
% emphasizes duality

Taking \verb|not : Bool -- Bool|, we say

$$\mathtag{true}~\mathtt{not} : -- \mathtt{Bool}$$

\verb|`true| has type \verb|-- `true| which can be generalized to $--\mathtag{true}\oplus\mathtag{false}$ (an acceptable argument to \verb|not : Bool -- Bool|). Sum types generalize but \textit{only on the right}. Compare the situation in linear logic \cite{ll}[p.~72]

\begin{mathpar}

\inferrule
{\vdash\Gamma,A \\ \vdash\Gamma,B}
{\vdash\Gamma,A\&B}

\inferrule
{\vdash\Gamma,A}
{\vdash\Gamma,A\oplus B}

\inferrule
{\vdash\Gamma,B}
{\vdash\Gamma,A\oplus B}
\end{mathpar}

Forbidding $\&$-generalization on the right manifests as forbidding inexhaustive pattern-matches. $\oplus$ is a disjunction; $\&$ is a conjuction; it restricts. \footnote{$\&$ is a product; it would be farcical for a programmer to supply \verb|1| when a term of type \verb|(Int * Int)| is required. Yet this is exactly what allowing inexhaustive and redundant pattern matches encourages!}

Recalling the identity rule\footnote{This pairs well with the fact that inverses exchange left and right, as pointed out by Ehrenberg\cite{ehrenberg2009}}.

\begin{mathpar}
\inferrule
{\\}
{\vdash A,A^\bot}
\quad(\textsc{Id})
\end{mathpar}

and the definition of $(-)^\bot$ by the De Morgan laws $(A\oplus B)^\bot = A^\bot \& B^\bot$ \cite{girard1987}[p.~20], we can prove that $\&$ (with) generalizes on the left. And indeed a function accepting a value of type $A\oplus B$ as argument can just as well accept a value of type $A$, though this is not manifest in, say, Haskell. But this turns out to be useful; we define \verb|foldr| to work on non-empty lists in \S\ref{sec:head}.

\subsection{Reusing Pattern-Match Arms}

We can define a function

\begin{verbatim}
if : a b `true -- a
   := [ { `true⁻¹ drop } ]
\end{verbatim}

This is not so useful on its own---it requires the programmer to supply exactly one value and then discards it---but see how it unifies:

\begin{verbatim}
else : a b `false -- b
     := [ { `false⁻¹ nip } ]

choice : a a Bool -- a
       := [ { if & else } ]
\end{verbatim}

Pattern-match arms are terms like builtin functions (\verb|+|, \verb|swap|, etc.) and can be reused (named); one enjoys cut elimination for sequences of such.

\subsection{Typesafe Head}\label{sec:head}

\begin{verbatim}
type List a = { `nil ⊕ List(a) a `cons };

type NE a = { List(a) a `cons };

head : NE a -- a
     := [ { `cons⁻¹ nip } ]
\end{verbatim}

Any nonempty list can be supplied as an argument to a function on lists. This is far more satisfactory than the situation in Haskell, in which \verb|foldr| \&c. must be defined for \verb|NonEmpty| and \verb|List| separately.\footnote{Typeclasses allow \verb|foldr| to be called on non-empty lists and lists equally but instances must be defined separately, and the typeclass machinery brings globality of instances and other complications.}

\subsection{Pattern Terms}

Suppose we have

\begin{verbatim}
type Ord = { `lt ⊕ `eq ⊕ `gt };
\end{verbatim}

Then we can define

\begin{verbatim}
lte : { `lt ⊕ `eq } --
    := [ { `lt⁻¹ & `eq⁻¹ } ]

gt : Ord -- Bool
      := [ { lte `false & `gt⁻¹ `true } ]
\end{verbatim}

So or-patterns are reusable, enjoy cut-elimination, etc.
